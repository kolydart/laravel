# In-app guide

User documentation that lives in the repository, next to the code it describes, and is read inside the application.

## What it is

Each `<slug>.md` file in a folder of the application (by default `docs/guide/`) becomes a page at `/{prefix}/guide/<slug>`, inside the application's own layout and behind its own authorization. There is no build step and no database table: the files are read on every request, so a page edited and deployed is a page published.

| Piece | Responsibility |
|---|---|
| `App\Support\Guide\GuidePage` | one page: front matter plus the Markdown body |
| `App\Support\Guide\GuideRepository` | scans the folder, validates the front matter, orders the pages, searches them |
| `App\Support\Guide\GuideRenderer` | Markdown (CommonMark + tables) to HTML; rewrites images and cross-links |
| `App\Http\Controllers\GuideController` | index with search, page, image |
| `Resources/views/guide/{index,show}.blade.php` | `kolydart::guide.index` / `kolydart::guide.show` |
| `src/routes/guide.php` | `{name}guide.index`, `{name}guide.show`, `{name}guide.asset` |

Dependencies: `symfony/yaml` and `league/commonmark`, both only suggested by the package, so that an application without the guide does not install them. `league/commonmark` comes with `laravel/framework`; `symfony/yaml` usually needs `composer require symfony/yaml`. With `enabled => true` and either one missing, the provider throws at boot with the package name.

The views are loaded by `KolydartServiceProvider` itself, so the guide needs only that provider.

## Setup

1. In `config/kolydart.php`, add the whole `guide` block. `mergeConfigFrom()` merges only the top level, so an application that has published the file gets **none** of the package's `guide` defaults; every key must be repeated.

   ```php
   'guide' => [
       'enabled'    => true,
       'path'       => null,                  // null => base_path('docs/guide')
       'gate'       => 'guide_access',        // checked on every route; null => any user past the middleware
       'admin_gate' => 'user_management_access', // reveals `visibility: admin` pages; null => nobody sees them
       'routes'     => ['middleware' => ['web', 'auth', 'backend'], 'prefix' => 'admin', 'name' => 'admin.'],
       'layout'     => 'layouts.admin',
       'sections'   => [                      // section key => heading, in menu order
           'overview' => 'Γνωριμία',
           'workflows' => 'Εργασίες',
       ],
   ],
   ```

2. Create the permission named in `gate` and assign it to the roles that should read the guide. With `AuthGates` the gate exists only once a role holds the permission; `Gate::denies()` on an undefined ability is true, so an unassigned permission locks everyone out, including the admin.
3. Add a menu entry, wrapped in `@can` with the same ability, pointing at `route('admin.guide.index')`.
4. Make sure the folder reaches production. It is read at request time, so a deployment that leaves out `docs/` publishes an empty guide.

**The layout** must `@yield('content')` and `@yield('styles')`; `title` is used when the layout yields it. AdminLTE layouts generated by QuickAdminPanel do all three.

## A page

```markdown
---
slug: roloi-kai-prosvasi
title: Ρόλοι και πρόσβαση
section: overview
order: 20
excerpt: Τι βλέπει και τι κάνει κάθε ρόλος.
visibility: private
source: [docs/features/auth-and-permissions.md]
---

Το κείμενο σε **Markdown**.
```

| Key | Required | Meaning |
|---|---|---|
| `slug` | yes | The address. Lower-case latin letters, digits, dashes; **must equal the file name** (`roloi-kai-prosvasi.md`). |
| `title` | no (slug) | Heading and menu entry. |
| `section` | no (`general`) | Menu group; headings and order come from `kolydart.guide.sections`. An unlisted section sorts last, under its raw key. |
| `order` | no (100) | Position inside the section, a whole number (negative allowed); ties sort by title. |
| `excerpt` | no | One line under the title in the index and in search results. |
| `visibility` | no (`private`) | `private`: everyone who passes `gate`. `admin`: also needs `admin_gate`. |
| `source` | no | Provenance for maintainers: the documents the page is written from, one path or a list. Never rendered. |

**A malformed page throws** (no front matter, invalid YAML, a slug that does not match its file, an unknown visibility, a list where a single value belongs, an `order` that is not a whole number, a link to a `.md` file that cannot be a page). A UTF-8 byte-order mark before the front matter is ignored. A page that silently fell out of the menu would be a gap nobody notices; the exception surfaces in a test that renders every page, before the page is deployed. Write that test in the application (see [Testing](#testing)).

`README.md` in the folder is skipped, so it can hold the application's own authoring contract.

### Links and images

Write addresses that also work in an editor's Markdown preview; the renderer rewrites them:

- `[Ρόλοι](roloi-kai-prosvasi.md)` or `[Ρόλοι](roloi-kai-prosvasi)`, with an optional `#fragment` → the page route. A bare `<name>.md` that is not a slug (`README.md`, `Roles.md`) throws instead of becoming a dead link; a path such as `../features/x.md` is left as written.
- `![Μενού](images/ploigisi/menu.png)` → the image route. Images live in `<path>/images/<slug>/`. They are served by the same controller, behind the same gate, never from `public/`. A file name may hold any character; write `#`, `?`, `%` and spaces percent-encoded (`a%23b.png`), as the Markdown preview needs anyway.

Every file under `images/` is served, `.svg` and `.html` included, with `Content-Security-Policy: default-src 'none'; …; sandbox`, so a script inside one does not run when the file is opened directly.

Headings get an `id` built as GitHub and the editor previews build it (lower case, punctuation dropped, spaces to dashes, Greek letters and accents kept; a repeated heading gets `-1`, `-2`), so `[…](#εγγραφή-και-τμήμα)` works in both places.

Everything else (`https://…`, `/admin/people`, `#top`) is left as written. HTML comments are removed from the output, so they can carry notes between maintainers. Raw HTML is allowed (the files are authored in git, not user input); `javascript:` links are not.

## Search

The index takes `?q=`. Matching ignores case, accents and final sigma (`εγγραφη` finds `Εγγραφές`); title matches rank first, then excerpt, then the number of matches in the body. Pages the user may not see are removed from the results.

## Visibility

| | `gate` passes | `gate` fails |
|---|---|---|
| `private` page | shown | 403 |
| `admin` page, `admin_gate` passes | shown | 403 |
| `admin` page, `admin_gate` fails or is null | **404**, and absent from menu and search | 403 |

A hidden page answers 404, the same as a missing one, so its existence is not disclosed. Its images (`images/<slug>/…`) answer the same way.

## Testing

The package tests the controller directly (`tests/App/Http/Controllers/GuideControllerTest.php`): 403 without the gate, 404 for a missing or hidden page, path traversal, null bytes, the images of a hidden page reached through `..`, `./` or upper case, and `?q[]=`. What only the application has stays the application's to test:

- the route middleware and the real gate with the real roles (200 / 403);
- the layout: one page renders inside it;
- **every real page renders**: iterate `GuideRepository::all()` and request each `show`. This is what turns a malformed page, or a link to `README.md`, into a failing build.

Point `kolydart.guide.path` at a fixtures folder for the first two; the repository is bound `scoped`, so a config change before the request is picked up.
